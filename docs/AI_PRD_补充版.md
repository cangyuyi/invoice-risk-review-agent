# 企业报销票据重复与异常风险审核：AI PRD 补充版

> 文档性质：独立补充文件。用于补齐现有原型的架构选择、节点契约、失败处理、人机协作、评测与上线门槛；不改变现有代码和已经产出的评测结果。
>
> 当前证据：5 张测试图片（4 张不同票据）；二维码三字段 5/5；Tesseract 三字段全对 2/5；豆包客户端三字段全对 2/5；确定性规则合成回归 36/36。以上均为小样本或合成评测，不能外推为生产准确率。

## 1. 先纠正产品定位

本项目最合适的架构不是多 Agent，而是：

**固定 Workflow + 两类局部决策 + Human in the Loop。**

- 固定 Workflow：上传、取证、字段提取、字段校验、批次查重、历史查重、权威状态检查、风险分流。
- 模型局部决策：二维码不可用时，才由 OCR/视觉模型尝试读取字段。
- 规则局部决策：重复判断、字段合法性和风险分级使用确定性规则，不交给大模型自由判断。
- 人工节点：字段冲突、低置信度、台账异常、未验真或高风险命中都进入人工复核。

不采用多 Agent 的原因：步骤固定、结果格式明确、财务场景要求可复现与可审计；引入自主规划只会增加成本和不可控性。

## 2. 用户、问题与边界

### 2.1 目标用户

- 一线财务审核人员：需要快速定位重复或异常票据，并看到可核验的证据。
- 财务负责人：需要知道规则为何拦截、谁处理过、何时处理以及最终结论。
- 报销员工：需要得到清楚的补充材料或驳回原因，而不是“AI 判断有风险”。

### 2.2 核心任务

把“逐张看票、复制票号、翻历史台账”的重复劳动，改造成先机器取证和筛查、再由财务做最终决定的审核流程。

### 2.3 明确不做

- 当前不支持识别发票真伪、红冲或作废状态。
- 当前不替财务人员作最终审批。
- 豆包客户端仅是人工触发的视觉基线，不是 API 或自动生产链路。
- 未接入税务权威查询前，真实图片流程自动放行率保持 0%。

## 3. 正常流程与异常流程

### 3.1 正常主线

```text
接收票据
→ 生成匿名记录号和文件哈希
→ 优先解析二维码
→ 校验票号、日期、金额
→ 批次内文件哈希/票号查重
→ 查询历史报销台账
→ 查询税务权威状态（当前未实现）
→ 生成规则、证据和建议动作
→ 自动放行或创建人工复核任务
→ 记录最终人工结论
```

### 3.2 异常分支

| 异常 | 系统动作 | 禁止动作 |
| --- | --- | --- |
| 图片损坏或无法打开 | 标记 `E01_FILE_UNREADABLE`，转人工补传 | 不得把空结果当成无风险 |
| 没有二维码或识别出多个有效二维码 | 最多进入一次 OCR/视觉降级；仍不确定则转人工 | 不得任选一个二维码 |
| 二维码与 OCR/视觉字段冲突 | 保留各来源原值，标记冲突，转人工 | 不得静默覆盖 |
| 票号、日期或金额不合法 | 触发 R00/R01，转人工 | 不得继续自动放行 |
| 历史台账不可用、超时或数据损坏 | 标记 `E05_LEDGER_UNAVAILABLE`，整条记录失败关闭 | 不得按“未查到重复”处理 |
| 未接入或未查到税务权威状态 | 触发 R40，转人工 | 不得把二维码可读写成发票有效 |
| 输出文件写入失败 | 本批次状态保持未完成并告警 | 不得只打印成功信息 |

## 4. 节点契约

每个节点必须同时定义输入、输出、完成条件、失败处理和指标。下表是本项目的最小可执行契约。

| 节点 | 输入 | 输出 | 完成条件 | 失败处理 | 核心指标 |
| --- | --- | --- | --- | --- | --- |
| N00 接收与取证 | 图片列表、批次号 | `record_id`、文件哈希、文件类型、证据引用 | 每张图片均有匿名编号和哈希 | 不可读转人工补传 | 接收成功率、重复文件率 |
| N10 字段提取 | 图片、文件哈希 | 票号、日期、金额、字段来源、不确定字段 | 三个关键字段均有来源；不确定性被显式记录 | QR 失败才降级；冲突转人工 | 字段精确匹配率、降级率、冲突率 |
| N20 字段校验 | 原始字段、来源 | 规范化字段、校验错误码 | 日期、金额、票号格式检查完成 | R00/R01 转人工 | 节点通过率、错误类型分布 |
| N30 批次查重 | 规范化字段、文件哈希 | R10/R11 命中证据 | 本批次所有记录完成对比 | 节点异常则批次不完成 | 批次重复命中率、处理时延 |
| N40 历史查重 | 票据键、台账快照版本 | R20/R30 命中记录和证据 | 查询成功并记录台账版本 | 台账异常时失败关闭 | 查询成功率、疑似重复率 |
| N50 权威状态 | 票据身份信息 | 有效/红冲/作废/未知及来源 | 返回可追溯的权威结果 | 当前未实现，一律 R40 | 查询成功率、结果新鲜度 |
| N60 风险分流 | 全部规则和证据 | 风险等级、建议动作、规则版本 | 每条记录均有动作和证据 | 缺任一关键结果则转人工 | 自动放行率、人工复核率 |
| N70 人工复核 | 复核任务、证据引用 | 人工结论、理由、人员、时间 | 结论、理由、审核人、时间均已保存 | 超时升级给负责人 | 处理时长、推翻率、积压量 |

## 5. 数据来源优先级与冲突规则

### 5.1 字段来源优先级

1. 税务权威接口：只负责有效、红冲、作废等权威状态；当前未接入。
2. 发票二维码：当前票号、日期、金额的首选结构化来源。
3. 本地 OCR：二维码损坏或缺失时的自动降级候选。
4. 豆包客户端视觉识别：仅用于人工评测和探索，不进入自动链路。
5. 人工录入：需要记录审核人和原始证据，不得覆盖历史值而不留痕。

### 5.2 冲突处理

- 任一关键字段来源之间不一致，结果必须进入人工复核。
- 保存“原始值、规范化值、来源、提取器版本”，不只保存最后一个值。
- 财务人员修正字段后，保留修改前后值和原因。
- “未命中历史台账”与“台账查询失败”是两种不同状态，严禁合并。

## 6. 风险规则和版本管理

现有 R00、R01、R10、R11、R20、R30 保留；端到端流程补充：

- R40：未获得税务权威有效、红冲和作废状态，进入人工复核。
- R41：关键字段来源冲突，进入人工复核。
- R42：历史台账不可用或快照损坏，失败关闭并转人工。

每次输出必须记录：

- `rule_version`：风险规则版本；
- `extractor_version`：二维码/OCR/模型与 Prompt 版本；
- `ledger_snapshot_id`：历史台账版本或更新时间；
- `run_id`：本次运行编号；
- `evidence_refs`：证据引用，不在公开报告中暴露真实票号。

R30 的“三天窗口”当前是探索性启发式规则，不是已经验证的行业标准。上线前应使用真实脱敏历史数据观察误报和漏报，再由财务负责人确认阈值。

## 7. 人工复核任务的最小数据结构

```json
{
  "review_task_id": "REV-DEMO-001",
  "run_id": "RUN-DEMO-001",
  "record_id": "INV-XX",
  "status": "pending",
  "trigger_rule_ids": ["R30", "R40"],
  "evidence_refs": ["private://evidence/INV-XX"],
  "assignee": null,
  "created_at": "ISO-8601 timestamp",
  "reviewed_at": null,
  "reviewer_decision": null,
  "review_reason": null,
  "rule_version": "v1"
}
```

公开演示可以展示匿名任务状态，但不得伪造审核人、审核时间或已经完成的人工结论。

## 8. 完成、失败与终止条件

### 8.1 单张票据完成条件

满足以下任一条件才算完成：

1. 权威状态已查、所有强制规则通过，且满足经财务批准的自动放行门槛；或
2. 人工复核任务已成功创建并持久化，状态为 `pending`；或
3. 人工复核已完成，结论和审计字段齐全。

### 8.2 批次完成条件

- 输出记录数与输入记录数一致；
- 每条记录都有明确状态、动作、规则版本和证据引用；
- 汇总数量与逐条结果能够对账；
- 输出文件成功写入后，才能返回“批次完成”。

### 8.3 降级终止条件

当前流程不需要 ReAct 自主循环。未来接入自动视觉模型时，每张票最多执行：

1. 一次二维码解析；
2. 一次 OCR/视觉降级；
3. 仍缺字段或存在冲突，立即转人工。

不允许无限重试，也不需要为了“看起来像 Agent”增加自我反思循环。

## 9. 评测补充

现有评测已覆盖字段路线对比、36 条规则回归和 5 图端到端演示，但还需四类补充。

### 9.1 模型重复运行一致性

豆包或其他视觉模型具有随机性。下一轮使用同一批图片、每张新建对话、每张重复 3 次，报告：

- 单字段精确匹配率；
- 三字段全对率；
- 三次结果完全一致率；
- 主动标记不确定的比例；
- 错误却未标记不确定的比例。

这 15 次运行仍是客户端人工评测，不写成 API 自动化能力。

### 9.2 失败注入集

至少补充以下可公开合成 Case：

- 损坏图片；
- 无二维码；
- 多个有效二维码；
- 二维码与 OCR 字段冲突；
- 历史台账日期或金额损坏；
- 历史台账不可访问；
- 输出目录不可写；
- 输入 0 张、1 张和多张图片。

验收重点不是“有没有报错”，而是是否失败关闭、是否创建人工动作、是否留下错误码。

### 9.3 节点级指标

- 节点通过率 = 成功完成该节点的记录数 / 进入该节点的记录数；
- 降级率 = 进入 OCR/视觉降级的记录数 / 总记录数；
- 人工复核率 = 创建人工任务的记录数 / 总记录数；
- 人工推翻率 = 人工结论与系统建议不同的任务数 / 已复核任务数；
- 证据完整率 = 含规则版本、来源和证据引用的结果数 / 总结果数；
- 端到端时延：报告 P50、P95，不只报平均值；
- 单票成本：本地解析、模型调用和人工复核分别计量。

### 9.4 环境隔离

- 每轮评测使用固定台账快照；
- 评测前清理上一轮输出和任务状态；
- 同一 Case 的重复运行不得互相读取答案；
- 规则、黄金集或 Prompt 改动后，必须用同一版本数据回归。

## 10. 试点门槛与业务指标

当前项目只有技术原型结果，不能声称节省了多少工时或拦截了多少损失。试点前先采集真实基线：

- 财务单张审核平均时长；
- 每批次翻查历史台账耗时；
- 重复报销实际发生率；
- 人工误判和返工率；
- 月度票据量及高峰并发。

建议的试点验收门槛需由财务负责人最终确认。可以先提出但不得写成已实现：

- 强制风险 Case 自动放行数为 0；
- 规则黄金集回归 100% 通过；
- 证据和审计字段完整率 100%；
- 关键字段精确匹配目标不低于 95%；
- P95 时延和单票成本在试点前根据真实业务量确定。

## 11. 成本与性能策略

按从便宜、稳定到昂贵、不确定的顺序调用：

```text
文件哈希/二维码（本地）
→ 本地 OCR（仅降级）
→ 视觉模型（未来 API，仅再次降级）
→ 人工复核
```

- 同一文件哈希可以复用提取结果，但风险判断必须使用当前批次和最新台账重新执行。
- 票据图片和真实字段不进入公开缓存。
- 只有接入 API 后才统计 Token 和模型费用；豆包客户端无限 Token 不能写成生产成本为零。

## 12. 埋点与审计日志

每个节点最少记录：

```text
run_id / record_id / node_id / status
started_at / finished_at / duration_ms
input_hash / data_source / extractor_version / rule_version
error_code / retry_count / next_action / evidence_ref
```

公开日志只保留匿名编号和统计信息；真实票号、二维码原文、购买方信息和图片只放私有目录。

## 13. 实施优先级

### P0：作品集闭环必须补

- 补节点契约、异常分支和终止条件：本文件已完成。
- 增加失败注入评测，重点验证台账异常不会导致空放行。
- 形成真实的人工复核任务状态和审计字段；未实现前明确标注原型边界。
- 豆包客户端做 3 次重复运行一致性评测。

### P1：进入真实试点前补

- 接入只读历史台账并记录快照版本。
- 接入税务权威状态查询，确认权限、限流和失败策略。
- 增加节点耗时、失败率、积压量和人工推翻率看板。
- 用脱敏历史数据校准 R30 阈值。

### 暂不做

- 多 Agent 动态编排；
- 向量数据库；
- LLM 自评循环；
- 自动替代财务终审。

这些能力当前不会提高核心查重可信度，反而会增加调试和审计成本。

## 14. 对照两篇笔记后的结论

两篇笔记中最值得吸收的不是 Agent 名词，而是五条产品原则：

1. 先按业务确定编排方式，固定流程不要强行多 Agent。
2. 每个节点必须写清输入、输出、完成条件和失败处理。
3. 最难的不是模型思考，而是判断结果是否完成、是否可信。
4. 高风险业务必须失败关闭，并设计清楚人工接管。
5. 上线只是开始，节点评测、失败注入、成本和持续回归同样属于产品方案。

本项目的方向正确：二维码优先、规则决策、证据留存和 0% 未验真自动放行都符合上述原则。真正需要补强的是“运行与治理层”，而不是再加模型或再拆 Agent。
